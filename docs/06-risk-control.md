# 06 · 风控与反调试

> 智慧树的风控体系分析。**本文如实区分"已证实"与"未定位"的部分。**

---

## 1. 反调试机制

### 1.1 现象：附着调试器会导致页面被销毁

用 Chrome DevTools Protocol 附着后：

```
document.documentElement === null     ← 文档被销毁
document.readyState === "loading"     ← 永远停在加载中
页面表现：白屏
```

**对照实验：**

| 条件 | 结果 |
|---|---|
| 附着 CDP + `Network.enable` | ❌ 白屏 |
| **不附着 CDP** | ✅ 正常 |

### 1.2 反混淆后定位到的机制

```javascript
// ① 定时校验原生 API 是否被 hook
setInterval(checkout, 60000);     // 每 60 秒一次

// ② 事件可信度校验
//    PointerEvent / MouseEvent 上的 isTrusted 检查
//    程序合成的事件 isTrusted === false → 判定为自动化

// ③ 命中后的 notTrustScript 流程
//    a) 上报：collector2c.zhihuishu.com/public/jsonp/collect
//    b) 暂停播放器
//    c) 页面跳转
```

### 1.3 ★ 关键结论：反调试完全实现在浏览器层

> **反调试代码运行在浏览器里。**
> **任何不经过浏览器的 API 客户端，天然绕过全部反调试机制。**

这不是"绕过技术"，而是**架构层面的必然结果**。

**方法学意义：**

| 方案 | 反调试影响 |
|---|---|
| 浏览器自动化（Playwright / Selenium / CDP） | ❌ 需要对抗 `isTrusted`、原生 API 校验、定时器检测 |
| **纯 API 客户端** | ✅ **完全不受影响** |

## 2. 行为风控

### 2.1 异常行为记录接口

```http
GET /cheat/exceptionActionDetail?schoolId=<id>&recruitId=<id>
```

**响应：**

```json
{ "count": 0, "lock": false, "punishType": 0, "popWindow": false }
```

| 字段 | 含义 | 健康值 |
|---|---|---|
| `count` | 异常行为累计次数 | `0` |
| `lock` | 是否被锁定 | `false` |
| `punishType` | 处罚类型 | `0` |
| `popWindow` | 是否弹窗警告 | `false` |

> **这是判断账号是否"干净"的权威接口。**
> 排查风控问题时，**应首先查这个接口** ——
> 如果 `count: 0` 且 `lock: false`，说明问题不在账号层面，
> 应转向排查**单次请求**的内容是否异常。

### 2.2 多开检测

服务端返回 **`-10`**，前端提示"同时播放多个视频，进度将停止记录"。

**检测维度（推测，未完全证实）：**
- 同一账号并发会话数
- 同一视频的并发播放

### 2.3 学习时长限制

```http
GET /course/queryStudiedTimeLimitInfo?recruitId=<id>&schoolId=<id>
```

返回 `canBeStudyNow` 等字段，超出允许的学习时间窗时返回 **`-9`**。

## 3. 验证码（易盾）

### 3.1 触发

业务接口返回 **`-12`**，前端弹出滑块。

校验接口：

```http
POST /learning/validateSlideToken
Body: { token, ev, checkType: 2 }
```

### 3.2 会话级状态

**实测观察**：`-12` 是**会话级**的，不是单次请求级的。

```
某次请求触发 -12
    ↓
后续所有写请求都返回 -12（即使内容完全正常）
    ↓
在浏览器中正常观看视频几分钟
    ↓
写请求恢复正常
```

**推测**：浏览器会加载易盾 SDK 并完成一次校验，从而刷新会话的风控状态。

> **这一现象被独立复现了两次**，可信度较高。

### 3.3 登录时的易盾门槛

**登录接口同样受易盾保护**（见 [02](02-login-and-session.md#221-账号密码登录含验证码门槛)）：

```
不带 validate      → {"status": -1}
带失效 validate    → {"status": -4, "msg": "滑动验证码校验失败"}
```

**结论：账号密码登录无法纯 API 完成。**

扫描登录则可以 —— 因为它走的是**移动端 App 的确认**，不经过 Web 端滑块。

## 4. 错误码总表

**本文档扩充了公开资料中未记录的错误码（标 ★）。**

| code | 含义 | 触发场景 | 处置建议 |
|---|---|---|---|
| `0` | 成功 | — | — |
| ★ **`-8`** | **学习总时长下降了** | 上报的 `totalStudyTime` 小于服务端已存值 | 先读当前值再递增 |
| `-9` | 学习时间已结束 | 超出课程允许的时间窗 | 停止，等待窗口开放 |
| `-10` | 同时播放多个视频 | 多开检测 | 确保单会话单视频 |
| `-12` | 需要滑块验证 | 易盾风控 | 浏览器正常观看几分钟后再试 |
| `403` | 登录过期 | 会话失效（24 小时） | 重新登录 |
| `422` | 参数或状态异常 | 请求内容不合法 | 检查参数 |

> ⚠️ **注意**：这些是**业务层错误码**，出现在 HTTP 200 的响应体里。
> 不要把它们与 HTTP 状态码混淆。

## 5. 未定位的部分

**如实标注研究中没有拿到确凿证据的问题：**

### 5.1 `-12` 的精确触发条件

**已排除的假设：**

| 假设 | 排除依据 |
|---|---|
| TLS 指纹不对 | 换用 Chrome 真实 JA3 + HTTP/2（`curl_cffi`）后行为一致 |
| 账号被标记 | `exceptionActionDetail` 显示 `count: 0`、`lock: false` |
| `totalStudyTime` 超过 `videoSec` | 实测服务端接受任意大的值 |
| 请求间隔过短 | 实测 60 秒内连发两次上报均成功 |

**当前状态：触发条件未完全定位。**

**实践中的经验性缓解措施**（有效但机制不明）：

> **减少冗余上报次数。**
> 在一次对照中，去掉"视频已达标后仍补发一次上报"的逻辑后，
> 同一会话连续 14 个视频的 27 次上报**零触发**。

**推测**：可能存在**累积风险分**机制，
即使单次请求完全合法，高频次也会推高分数。

> ⚠️ 这是**基于观察的经验规律**，不是已证实的机制。**请谨慎对待。**

### 5.2 其他未验证项

- 易盾 `validate` token 的生成算法（依赖混淆的 SDK 与浏览器环境）
- 风控的具体评分维度与阈值
- `SERVERID` / `acw_tc` 等路由 cookie 是否参与风控判定

## 6. 研究者的实践准则

**本次研究全程遵守的自我约束：**

1. **只用研究者本人的账号**，不涉及任何第三方
2. **命中 `-12` 立即停止**，不硬试、不改写参数绕过
3. **不尝试破解易盾滑块**（未做任何滑块识别/打码尝试）
4. **不使用多账号**（避免触发 `-10`）
5. **遇到账号层面的异常立即停手**并复查 `exceptionActionDetail`
6. **不做高频请求**，节奏严格对齐真实客户端（300 秒）

> **技术上能做 ≠ 应该做。**
> 本研究的目的是理解机制，而非对抗风控。
